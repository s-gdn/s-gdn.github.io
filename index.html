Procedural Level Design

I created this project to put my level design abilities to the test.

It uses Gaia to create large, procedural, realistic landscapes, which can be very resource intensive if not done right.

So I implemented a system which splits up the large terrain into multiple regions. The regions closest to the player camera are loaded in full resolution, but the regions past a certain distance are created as "imposter" regions, being at a lower texture and mesh resolution. These regions are updated dynamically as you move around the map, unloading imposter terrain as you get closer, and replacing it with the higher resolution terrain.

Apart from that, I am also using Unity's HDRP water to render the ocean and rivers, with underwater caustic effects for when the player is underwater.

I have also included terrain objects such as trees, rocks, mushrooms, and soon grass, when I can find a texture that doesn't affect performance too much. These objects are placed procedurally depending on terrain biome, height of terrain, and angle of terrain, ensuring objects are placed realistically. All current objects have an LOD system, meaning the further away from the object you are, the smaller resolution the mesh is, once again, making performance smooth.

And finally, we have particle and sound effects. Particle effects include birds in the sky, butterflies in open fields, and airborne spores in the woodlands. Atmospheric sound effects are dynamic and change depending on the biome you are in.

Overall I am happy with my progress on this project, having never made a procedural terrain before, its interesting to see how realistic a terrain can look, even when its generated automatically without me manually placing anything, while also running smoothly at over 60fps.



Source Engine Based Movement

This project was designed to hone my coding skills related to the movement of a player, by attempting to emulate the movement of games made with the Source Engine, such as Counter Strike and Half Life, which many people say has some of the most fun movement of any games.

The Source Engine movement is interesting, as strafing (moving the mouse left of right, along with syncing the a and d keys with said mouse movement) allows you to gain velocity (speed) in mid air. If you jump as soon as you hit the ground, you can carry this speed into your next jump, allowing you to chain these jumps, and get to some very high speeds. As well as that, you can "surf" on objects that are at a certain angle, if you hold the key that would push you towards the object, as you can see in the demonstration video. This also allows you to gain speed.

I created a simple test scene to demonstrate this, complete with just a platform, and a surfable object. The first thing on the agenda was to review the Source Engine's movement code, which luckily, is readily available and open source. Unity's default movement system is nothing like Source Engine's, but its a good base, So I used this for our start, and modified some values such as friction and movement speed, to emulate Source's base movement more closely.

Lastly I had to implement strafing and surfing mechanics, of which I just looked at the Source Engine's code, and copied these functions in Unity context in C#.

Please view the demonstration video to see these mechanics in effect.

Kernel Driver


The goal of this project was to make a c++ kernel driver I could run in ring-0 of a windows system, in order to interact with certain program's memory through said driver, without triggering any security measures like usermode anti-cheat systems or built in measures.

A kernel driver is essentially a piece of software ran at the kernel level of an operating system, which is the most privileged and low-level part of the system.

My intentions were to create a driver I could load using KDMapper, which is a readily available piece of software which uses a vulnerable driver already signed by Windows to create our own, malicious one. Which was easy enough. I used a virtual machine when testing, ensuring my actual PC wasn't at risk.

I started by setting up simple debug functions so I could debug the program along the way, and then I created the fake entry point as required by KDmapper. Inside this function we create a new driver using IoCreateDriver(&driver_name, &driver_main), where driver_name is just the custom name of our driver and driver_main is our "real" entry point function.

Driver_main() is used to set up the driver object, device object, symbolic link, and register handlers.

The last function we need is device_control(), which is used to set up I/O control functions for: Storing a reference to our target process (the program we want to modify), copying memory from the target process to our current process (read memory), and finally copying memory from our current process to the target process (write memory).

And without going into too much more detail, thats how the driver works! We can now utilise this by loading it with KDmapper, and then creating a usermode exe that interacts with the driver:



All thats left to do is decide what to use it for! The application I would want to exploit would have to be something with good usermode security, but no kernelmode security, as kernelmode security can detect drivers such as the one we have created, as well as any IOCTL calls made by it.

So I settled on Counter Strike 2, a relatively new game with a usermode anticheat.

I created a new c++ project in Visual Studio, set to compile as an executable. I created functions to interact with our driver and call its read / write functions, as well as passing CS2's handle to our driver.

Finally we need to find variables in the game that we want to change to our liking. Which means reverse engineering the game code. I used a powerful program called IDA pro, which essentially disassembles binary files like .exe, .dll and .sys, and turns it into human-readble assembly code. We can use this to piece together the structure of the program. This program in combination with others like cheat engine allow us to find the module address, offset of function from module, and offset of variable from function. So the full absolute address of a variable ususally looks like this:

(Module Address + function / structure offset + variable offset)

I wanted to create a cheat called a bunnyhop, which forces a jump as soon as the player touches the ground, carrying the velocity instead of slowing the player down.

In order to do this we would need a couple of variables. Player state flags tell us whether the player is on the ground or in the air, and Force Jump is self explanatory. After finding these, the rest is just the logic.

If(read(Module + PlayerClass + PlayerFlags) == !FL_ONGROUND) & user holding the space key, then: write(dwForceJump = our custom value to initiate jump)

And thats all! This code runs fine, and is not detected by the games anticheat. This would be considered an external cheat, but I have also made a simple usermode internal cheat, which allows more flexibility as you can hook the actual function in the game and modify them directly, but is less secure.
